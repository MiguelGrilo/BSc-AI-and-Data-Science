# 2. Requisitos de Sistema

## 2.1 Requisitos Funcionais (RF)

### RF 1.0 - Autenticação e Autorização
| RF | Descrição |
|:-:|-|
| **1.1** | O sistema deve exigir autenticação para aceder ás funcionalidades de administrador, operador e participante. |


### RF 2.0 - Gestão de Eventos
| RF | Descrição |
|:-:|-|
| **2.1** | O sistema deve permitir ao administrador definir diferentes fases de inscrição (early, late ou durante o evento) e associar a cada fase preços distintos para os tipos de inscrição (estudante ou não estudante). |
| **2.2** | O sistema  deve permitir ao administrador associar opções adicionais a um evento, definir o preço individual e indicar se a opção é opcional ou obrigatória. |


### RF 3.0 - Inscrição do Participante
| RF | Descrição |
|:-:|-|
| **3.1** | O sistema deve permitir aos participantes visualizar eventos cujas inscrições estejam abertas. | 
| **3.2** | O sistema deve identificar automáticamente qual a fase de inscrição em vigor e calcular qual o valor a pagar. | 
| **3.3** | A inscrição deve ficar registada com o estado inicial de “pendente de pagamento” até que a transferência seja verificada pelos administradores. | 
| **3.4** | Após ser confirmada, a inscrição deve passar para o estado de “paga”, permitindo a entrada no evento. | 
| **3.5** | O sistema deve fornecer ao participante instruções de pagamento que incluam o IBAN e a descrição obrigatória da transferência bancária. | 


### RF 4.0 - Gestão de Pagamentos
| RF | Descrição |
|:-:|-|
| **4.1** | O sistema deve permitir ao administrador consultar listas de participantes e verificar o estado do pagamento (pendente ou pago). | 
| **4.2** |  O administrador deve ter a capacidade de registar manualmente as transferências bancárias recebidas, confirmando o pagamento. O registo inclui o valor transferido, a data de transferência, notas do administrador e confirmação da transferência. | 
| **4.3** | O sistema deve calcular automaticamente o valor aplicável a cada inscrição com base na data em que o participante se inscreve. | 
| **4.4** | Após a confirmação manual da transferência pelo administrador, o estado da inscrição deve ser atualizado para “pago”. | 


### RF 5.0 - Check-In
| RF | Descrição |
|:-:|-|
| **5.1** | O sistema deve permitir aos administradores a exportação ou impressão de listas de participantes incluindo detalhes relevantes para a logística do evento. | 
| **5.2** |  A funcionalidade de check-in deve permitir ao operador pesquisar participantes inscritos por nome ou email. | 
| **5.3** | O operador apenas pode registar o check-in de um participante se o estado da sua inscrição for “paga”. | 
| **5.4** | Em caso de pagamento excecional no local, o operador deve registar o comprovativo de transferência bancária realizado no momento antes de completar o check-in. |

## 2.2 Requisitos Não Funcionais (RNF)

### RNF 1.0 - Requisitos de Produto
| RNF | Descrição |
|:-:|-|
| **1.1** | O sistema exige pagamento único e exclusivo das inscrições por transferência bancária. |
| **1.2** | A plataforma deve estar acessível 24h por dia. |
| **1.3** | A interface para administradores deve ser desenhada de modo a permitir o registo rápido e eficiente das transferências bancárias. |
